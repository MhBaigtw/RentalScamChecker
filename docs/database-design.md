# Database design

Postgres 16 (+ pgvector, first used in M5). Schema is defined in
`apps/api/rentalscamchecker/models.py` and created by Alembic migrations in
`apps/api/alembic/versions/`. CI runs `alembic upgrade head` and then `alembic check`, which
fails if the models and the migrations have drifted apart.

## Conventions

- **Primary keys**: UUID (v4, generated in Python) for anything whose id leaves the system
  (`checks.id` is in URLs, and a random id doesn't reveal how many checks exist). Bigint identity
  for internal tables (`jobs`, `reference_rents`), where ordering and compactness matter more.
- **Enumerations**: `TEXT` + `CHECK (col IN (...))`, not Postgres `ENUM` types (ED-012).
- **Constraint names** come from a naming convention on `Base.metadata`
  (`ck_<table>_<name>`, `fk_<table>_<col>_<ref>`, `uq_...`, `pk_<table>`), so migrations can refer
  to them by a predictable name.
- **Timestamps**: `timestamptz`, defaulting to `now()` on the server.
- **Money**: integer cents (`rent_cents`). Never floats.
- **Child rows** (`check_photos`, `check_contacts`, `signal_results`) reference `checks.id` with
  `ON DELETE CASCADE`: deleting a check removes everything about it in one statement.

## Tables (after M7)

### `checks`: one submitted listing and, later, its report
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| created_at | timestamptz | default `now()` |
| status | text | `pending` \| `running` \| `complete`. Default `pending`. M2 drives the transitions. |
| risk_level | text null | `low` \| `some` \| `high` \| `incomplete` (SPEC 5); set by the aggregator (M7) |
| independent_risk_level | text null | same values; the level from the check's own evidence, without results that depend on other checks. The only level other checks read (ED-027) |
| risk_details | jsonb null | contributing and missing signal names, `graph_capped` (no points or weights) |
| scoring_version | text null | which scoring config produced `risk_level` |
| user_id | uuid null | **no FK yet**: `users` arrives in M8 |
| submitted_url | text null | stored as text, never fetched |
| listing_text | text | ≤ 20 000 chars (validated in the API); phones/emails replaced by `[phone]`/`[email]` (ED-016) |
| rent_cents | int | `CHECK > 0` |
| bedrooms | smallint | `CHECK 0..10`, 0 = studio |
| unit_type | text | `whole_unit` (default) \| `room` \| `basement` (M3) |
| address_text, city | text | as typed by the user (trimmed) |
| geocoded_lat, geocoded_lon, geocoded_city, geocoded_at | null | filled by the geocoder (M3) |

### `check_photos`
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | also the file name in storage |
| check_id | uuid FK → checks | cascade |
| position | smallint | upload order; `UNIQUE (check_id, position)` |
| storage_key | text UNIQUE | `checks/<check_id>/<photo_id>.jpg` |
| phash, dhash | bigint null | 64-bit perceptual hashes (M5). Postgres has no unsigned 64-bit type; M5 will map unsigned → signed two's complement. XOR + `bit_count` still works on the signed value. |
| width, height | int | of the re-encoded image |

| embedding | vector(512) null | CLIP ViT-B/32 image embedding, L2-normalised (M5, ED-025); NULL until photo_reuse_internal has run |

Indexes (M5): `ix_check_photos_embedding_hnsw` (HNSW, `vector_cosine_ops`) for nearest-neighbour
search. No index for the hashes: a full `bit_count((phash # :q)::bit(64))` scan measured 7 ms at
10k rows and 47 ms at 100k rows, faster than a BK-tree (eval/reports/hash_search_bench.md).

### `check_contacts`
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| check_id | uuid FK → checks | cascade; `UNIQUE (check_id, kind, hmac_hash)`: each distinct contact once per check |
| kind | text | `phone` \| `email` |
| source | text | `field` (form fields) \| `text` (found in `listing_text`). In both → one row, `field` |
| hmac_hash | bytea | HMAC-SHA256 of `"<kind>:<normalized value>"`, `CHECK octet_length = 32` |

There is no column for the raw value. See "Privacy" below.

Indexes (M6): `ix_check_contacts_hmac_hash_check_id (hmac_hash, check_id)`: "which checks used this
contact?" for `contact_reuse` and the check graph. `kind` isn't in it: the HMAC input starts with
the kind, so equal hashes always have equal kinds. `check_id` is, so the lookup is index-only.

### `photo_links` (M6, ED-026)
| Column | Type | Notes |
|---|---|---|
| photo_id, other_photo_id | uuid FK → check_photos | cascade; PK `(photo_id, other_photo_id)` |
| check_id, other_check_id | uuid FK → checks | cascade; copied from the photos so graph queries skip the join; `CHECK (check_id <> other_check_id)` |
| match_type | text | `hash` \| `embedding` (which part of the M5 rule matched) |
| phash_distance, dhash_distance | smallint null | null for embedding-only matches |
| cosine | double null | |
| created_at | timestamptz | |

Every match is stored twice, A→B and B→A, by `graph.store_photo_links` (idempotent). Index
`ix_photo_links_check_id_other_check_id (check_id, other_check_id)`.

### `signal_results`
One row per (check, signal, signal version); `UNIQUE (check_id, name, version)`, so a re-run of
the same signal version can't insert a duplicate. `status` ∈ `ok|skipped|error`;
`severity` ∈ `none|low|medium|high` (NULL when the signal errored or was skipped);
`evidence jsonb` default `{}`. Written by workers from M2 on.

### `jobs`
The Postgres job queue (ED-002, ED-017). Repository: `jobs/queue.py` (plain SQL).

| Column | Meaning |
|---|---|
| id | bigint identity; tie-breaker in claim order |
| kind | `signal` or `aggregate` (handler lookup) |
| payload | jsonb: ids only (`check_id`, signal name/version). Never contact values. |
| idempotency_key | UNIQUE. `signal:<check>:<name>:<version>`, `aggregate:<check>`. Enqueue is `ON CONFLICT DO NOTHING`. |
| status | `queued` → `running` → `done`; `failed` = last attempt failed, retried at `run_after`; `dead` = dead-letter |
| attempts / max_attempts | incremented at claim; `attempts` is also the fencing token for complete/fail |
| run_after | when the job becomes claimable (enqueue delay, backoff, or the aggregator's timeout) |
| locked_until | lease end while `running`; NULL otherwise |
| last_error | `"<ExceptionType>: <message>"`, ≤ 2000 chars; kept after success for history |

`updated_at` is bumped explicitly in every SQL statement (ORM `onupdate` doesn't fire for raw SQL).

### `reference_rents` (M3, ED-021)
CMHC Rental Market Survey average rents, one row per geography × rent basis × bedroom bucket × survey.

| Column | Notes |
|---|---|
| geography_type | `cma` or `csd` (municipality) |
| geography_code / geography_name | StatCan CSD or CMA code / name |
| cma_name | the CMA a municipality belongs to (used for the fallback) |
| source_geography | the CMHC table row the value came from, e.g. `Zone 29 - Milton/Halton Hills` (zones can be shared) |
| rent_basis | `vacant_units` (table 3.1.9, asking rents of empty units) or `all_units` (table 3.1.2) |
| bedrooms | 0 studio, 1, 2, 3 = "3 bedroom +" |
| avg_rent_cents, reliability | NULL together when CMHC suppressed the value (`**`); reliability `a`-`d` |
| survey_year, survey_month | e.g. 2025, 10 |
| source, source_url | provenance of every row |

`UNIQUE (geography_type, geography_code, rent_basis, bedrooms, survey_year, survey_month)`, so
reloading the CSV is an upsert. Lookups filter on `lower(geography_name)` without an index: the table
holds 120 rows per survey, so a sequential scan is cheaper than maintaining an index.

### `geocode_cache` (M3, ED-022)
`(query_key, provider)` primary key → raw JSON response (a list, possibly empty), `created_at`. Holds
OpenStreetMap data (ODbL). No expiry yet.

### `worker_heartbeats` (M3, ED-023)
`worker_id` (`host:pid:random`) primary key; `started_at`, `last_seen_at`, `stopped_at`, `concurrency`,
`jobs_done_total`, `jobs_failed_total`, `jobs_timed_out_total`, `abandoned_threads_alive`. Upserted by
each worker process every 5 s; read by `GET /internal/metrics`.

### `web_image_searches`, `web_image_search_cache` (M5, ED-025)
Paid reverse image search (TinEye, OFF): one row per call (`provider`, `image_sha256`, `outcome`,
`result_count`, `error`, `called_at` indexed) for the daily cap; cache keyed by
`(image_sha256, provider)` with normalised matches. Empty until the feature is turned on.

### `rate_limits` (M3, ED-022)
`name` primary key → `last_request_at`. One row (`nominatim`); locked for the duration of each
geocoding request to enforce 1 request/s across processes.

### `llm_cache` (used from M4, ED-024)
Primary key `(content_hash, prompt_version, model)`: `content_hash` is the SHA-256 of the
(redacted) listing text, so a new prompt version or model never reads a stale answer. `response` is
`{"flags": [{"flag", "quote"}]}` exactly as returned (quotes are verified when used). Only successful
calls are cached.

### `llm_calls` (M4, ED-024)
One row per API call attempt: `called_at`, `model`, `prompt_version`, `outcome` (`started` → `ok` |
`refused` | `truncated` | `invalid` | `error`), `input_tokens`, `output_tokens`, `latency_ms`,
`error`. The daily cap counts rows since UTC midnight under a transaction-scoped advisory lock;
`ix_llm_calls_called_at` makes that count an index range scan as the table grows.

## Indexes

Postgres doesn't index foreign keys automatically. Each child table's unique constraint begins
with `check_id`, and the B-tree index behind that constraint also serves "all rows for this
check" lookups (`GET /checks/{id}`), so there are no separate `check_id` indexes.

Indexes are added in the milestone that writes the query that needs them, with `EXPLAIN` output
recorded here (job queue: M2; check graph: M6).


### Job queue indexes (M2)

```sql
CREATE INDEX ix_jobs_claimable     ON jobs (run_after, id) WHERE status IN ('queued', 'failed');
CREATE INDEX ix_jobs_running_lease ON jobs (locked_until)  WHERE status = 'running';
```

Both are **partial**: over time almost every row is `done` or `dead`, and those rows never need
to be found by the claim or the reaper. The index then holds only the handful of live jobs, so it
stays tiny and its first entry is the next job to claim. `(run_after, id)` matches the claim's
`ORDER BY run_after, id`, so Postgres reads the first matching index entry instead of sorting.

Evidence, measured 2026-10-16 on the dev machine (Postgres 16.15 in Docker) with 202,158 job rows
in the test database: 200,000 `done`, 2,000 `dead`, 50 due `queued`, 50 `queued` for the future,
8 `running`. Then `ANALYZE`, and `EXPLAIN (ANALYZE)` inside a transaction that was rolled back:

machine, not a benchmark; the M9 load test measures end-to-end throughput.

## Privacy

- Phone numbers and emails are normalized and HMAC-hashed **while the request is being handled**
  (`checks/service.py`). The raw values are never written to any table or to the logs. That is
  stricter than SPEC's "not persisted beyond the processing job". Verified in M1 by a test that
  dumps every row belonging to a check as JSON and searches it for the raw values, and by the same
  query by hand against the dev database.
